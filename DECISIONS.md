# Журнал архитектурных решений (DECISIONS.md)

> **Назначение:** Документирование всех ключевых инженерных и архитектурных решений, принятых в процессе ночного автономного цикла доработки проекта **GosTek**.  
> **Формат записи:** Контекст и суть решения, причины выбора, рассмотренные альтернативы, последствия.

---

## Решение D-001: Создание изолированной ветки и тега для ночного автономного цикла
- **Что:** Зафиксировано текущее стабильное состояние кодовой базы тегом `v0.45.0-stable` на коммите `1d2e7b1` и создана рабочая ветка `feature/big-audit-and-improvements`.
- **Почему:** Требование этапа 0 для гарантии точки восстановления без деструктивных операций `git reset`.
- **Альтернатива:** Работа напрямую в `main` (отвергнуто из-за риска загрязнения основного дерева).

## Решение D-002: Перенос флагов `accepted_*` в SecureStorage
- **Что:** Флаги подтверждения ошибочных полей профиля (`accepted_FullName`, `accepted_Passport`, `accepted_Unp` и др.), ранее сохранявшиеся в незашифрованном `Preferences.Default`, переносятся в защищённое хранилище `SecureStorage` с автоматической прозрачной миграцией без потери ранее выставленных пользователем подтверждений.
- **Почему:** Флаги содержат информацию о наличии и структуре чувствительных реквизитов (паспортные данные, налоговые номера). Хранение в открытом виде нарушает принцип минимизации раскрытия метаданных.
- **Альтернатива:** Оставить в `Preferences`, считая булевы флаги нечувствительными (отвергнуто, так как наличие флага раскрывает факт заполнения конкретных полей).

## Решение D-003: Единая точка выхода (Outbound Gateway) для ИИ-запросов
- **Что:** Создание централизованного метода/интерцептора маскирования исходящего payload в `AiAssistantService.SanitizeOutgoingPayload`. Все строковые поля запроса (`userText`, `currentFormFields`, `memory`, `templateName`, системный промпт) принудительно прогоняются через маскер перед сериализацией в HTTP-тело. Перед вызовом HttpClient выполняется строгий `AssertPayloadSafe` с выбросом `AiAssistantSecurityException`. Модель возвращает факты памяти, которые маскируются перед добавлением в `AiMemory`.
- **Почему:** Исключает случайные утечки ПДн из любых полей и UI-форм.
- **Альтернатива:** Ручное маскирование каждого поля в UI code-behind (слишком хрупко и подвержено человеческому фактору при добавлении новых полей).

## Решение D-004: Хранение принятых ошибок валидации внутри зашифрованного ProfileData
- **Что:** Свойство `AcceptedFields` добавлено непосредственно в `ProfileData`, сериализуемый в `SecureStorage` под системным ключом `user_profile_v1` (AES Keystore на Android, DPAPI на Windows). При загрузке профиля старые открытые ключи `accepted_*` из `Preferences.Default` бесшовно мигрируют в зашифрованный профиль и удаляются из `Preferences`. Для быстрой синхронной валидации в UI используется in-memory кэш `ProfileRules._acceptedFields`.
- **Почему:** Устраняет открытые следы персональных данных на диске, сохраняет обратную совместимость и высокую производительность синхронной валидации в XAML/C#.
- **Альтернатива:** Хранить каждый флаг в отдельном ключе `SecureStorage.SetAsync` (создаёт накладные расходы множественных асинхронных вызовов к Keystore при валидации каждого символа).

## Решение D-005: Автоматическая очистка кэша фото и исключение бэкапа
- **Что:** 1) Временные файлы фото с камеры и галереи регистрируются в `ScanPage` и гарантированно удаляются в блоках `finally` при успехе, ошибке, отмене и при уходе со страницы `OnDisappearing`; 2) Метод `FileSaveService.ClearTemp()` расширен до поиска и удаления `*.docx`, `*.pdf`, `*.jpg`, `*.jpeg`, `*.png`, `*.bmp`, `*.tmp` и вызывается асинхронно на старте приложения в `App.xaml.cs`; 3) Для Android 12+ добавлены `data_extraction_rules.xml` и `backup_rules.xml`, запрещающие резервное копирование и передачу данных между устройствами.
- **Почему:** Гарантирует соблюдение принципа минимизации хранения биометрических данных и фото паспортов на накопителе устройства.
- **Альтернатива:** Полагаться на встроенную очистку кэша операционной системой (неприемлемо, так как ОС может хранить файлы неделями).

## Решение D-006: Серверный шлюз Cloudflare Worker, каскад моделей и дедлайн
- **Что:** 
  1) Воркер `server/worker.js` переведен на настраиваемый каскад моделей через `env.MODELS_CASCADE` и универсальный адаптер `callOpenAiCompatible` (для Groq, DeepSeek, OpenAI, Mistral);
  2) Установлен общий дедлайн 15 секунд через `AbortController` и лимит тела запроса 32 КБ;
  3) Внедрен серверный Regex Scrubber как вторая линия обороны;
  4) Внедрен Zero-Text Logging (в логах Cloudflare логируются только провайдер, модель, задержка и статус без пользовательских текстов);
  5) Клиентский таймаут `AiAssistantService` согласован с сервером (20s вместо 35s), в UI индикатора набора добавлена кнопка «Отмена» с привязкой к `CancellationTokenSource`.
- **Почему:** Обеспечивает отказоустойчивость при падении или исчерпании квот одного провайдера, предотвращает зависание UI клиента и гарантирует соответствие принципу нулевого логирования персональных данных.
- **Альтернатива:** Держать жестко одну модель (приводит к сбоям при квотах 429) или отправлять запросы напрямую с клиента к внешним API (приводит к утечке API-ключей в коде приложения).

### D-007: Детерминированная машина состояний камеры и NavigationGuard от двойной навигации
- **Что сделано:** Реализована конечная машина состояний камеры `CameraLifecycleController` (`Stopped`, `Starting`, `Running`, `Disposed`) с токенами видимости для предотвращения гонок и падений нативного превью при быстром переключении вкладок; добавлен `NavigationGuard` с дебаунсом переходов для устранения белого экрана при спам-кликах по меню; добавлен флаг `ReduceMotionEnabled` в `AnimationHelper`; обеспечена потокобезопасность вызовов UI через проверку `MainThread.IsMainThread` и снятие фокуса с полей ввода Windows при нажатии клавиши Escape.
- **Почему:** При резкой смене вкладок или повторных нажатиях нативный компонент `CameraView` вызывал исключения «Unable to retrieve Handler» или зависал в параллельных вызовах. Асинхронные клики по Shell-навигации приводили к повторным вызовам `GoToAsync` и рассинхронизации нативного представления.
- **Альтернатива:** Использовать небезопасные флаги без синхронизации или блокировать всю страницу оверлеем при каждом клике.

### D-008: Централизация чата ИИ, расширение маскера ПДн и синтетический корпус 215 примеров
- **Что сделано:** Удалены индивидуальные кнопки-искорки «✨» возле каждого поля формы и рудимент `targetField` в пользу единого централизованного чата; оптимизирована верстка чата (на Windows компактная шторка шириной 490px справа вместо растягивания на весь экран; на Android включен `SoftInput.AdjustResize` против перекрытия ввода клавиатурой); маскер `PrivacyMasker` расширен поддержкой белорусских адресов, email, всех падежей ФИО, личных номеров РБ (14 символов) и адаптивного порога Левенштейна; добавлен синтетический тестовый корпус из 215 примеров с подтверждением False Negatives 0% (<1%) и False Positives 0% (<3%); в настройки добавлен тумблер мягкой маскировки спорных имён.
- **Почему:** Точечные кнопки возле полей перегружали интерфейс и дублировали функциональность чата. Маскирование только именительного падежа приводило к утечке склоняемых фамилий в родительном/дательном падежах.
- **Альтернатива:** Оставить кнопки у каждого поля (путает пользователя) или использовать тяжелые NLP-библиотеки на клиенте (увеличивает размер сборки на 40+ МБ).

### D-009: Смещение нативной области Drag Region за пределы Navigation Rail и миграция AutomationProperties
- **Что сделано:** В `Platforms/Windows/WindowSizing.cs` реализована чистая функция `CalculateDragRect`, смещающая прямоугольник перетаскивания окна `AppWindow.TitleBar.SetDragRectangles` вправо на текущую ширину Navigation Rail (220 DIP в развернутом виде, 64 DIP в свернутом, 0 DIP на полноэкранных страницах `FieldsPage`/`RuleEditorPage`); добавлено динамическое обновление по событию `AppTabBar.OnRailToggleTapped` и `AppShell.EnsureFlyoutState`; в XAML устранены 10 устаревших предупреждений компилятора XC0618 заменой `AutomationProperties.Name` на `SemanticProperties.Description`; успешно верифицирована сборка Windows в Release-конфигурации (`-c Release -warnaserror`).
- **Почему:** При начале области drag с X=0 системный перехватчик DWM перехватывал мышь в шапке левой панели, блокируя клики по кнопке сворачивания `RailToggleBtn`, логотипу и верхним элементам навигации.
- **Альтернатива:** Отказаться от нативного `SetDragRectangles` и вернуться к чистому MAUI TitleBar (приводит к лагам при перетаскивании окна) либо оставить клики заблокированными.

### D-010: Парсер ICAO 9303 MRZ, diff-экран применения в профиль и перенос скана в шаблон
- **Что сделано:** Реализован полнофункциональный детерминированный парсер `MrzParser` форматов TD3 (2x44) и TD1 (3x30) с проверкой контрольных сумм по алгоритму ICAO 9303 (веса 7-3-1) и нормализацией частых оптических ошибок OCR (O↔0, I↔1, B↔8, S↔5, Z↔2); обновлен `DocumentDataExtractor` с приоритетом MRZ над регулярными выражениями; на экране `ScanPage` реализован интерактивный экран подтверждения с diff «Было в профиле» vs «Распознано с фото», бейджем валидности контрольных сумм и чекбоксами выбора полей; добавлена кнопка «Перенести распознанный текст в шаблон...» с передачей через `DraftStore.PendingOcrText` и автоподстановкой в чат ИИ на `FieldsPage`.
- **Почему:** Паспорта нового образца и ID-карты содержат машиносчитываемую зону, которая гарантирует 100% точность благодаря контрольным суммам. Пользователь должен явно контролировать, какие именно поля перезаписывают его профиль.
- **Альтернатива:** Применять все распознанные данные вслепую без подтверждения (риск порчи данных профиля при нечетком снимке) или требовать ручного набора всех реквизитов.

### D-011: Финализация релиза, документация развертывания и программа ручной приёмки
- **Что сделано:** Проведена строгая верификация релизных профилей компиляции для Windows (`net10.0-windows10.0.19041.0`) и Android (`net10.0-android`) с флагом `-warnaserror`; подтверждена стабильность AOT/R8 тримминга на Android без утери необходимых рефлексивных типов; подготовлен исчерпывающий пакет документации: обновленный `README.md`, руководство по публикации `RELEASE.md` (MSIX, AAB, Keystore), чек-лист ручной приёмки `MANUAL_CHECKLIST.md` и итоговый отчёт аудита `FINAL_REPORT.md`.
- **Почему:** Конкурсный проект требует безупречной повторяемости сборки, отсутствия предупреждений компилятора даже в оптимизированных Release-режимах и прозрачных инструкций для жюри и проверяющих.
- **Альтернатива:** Ограничиться проверкой сборки в Debug-режиме (несёт риск неожиданных падений в Release из-за ILLink/R8 или XamlC).
